# issue-labeling

GitHub issue を読んで、**Priority / Difficulty / 要人間判断（or AI完結可）** の3種類のラベルを判定し、付けるスキル。

設計の元ネタは `geolonia/takamatsu-city-flood-prevention-headquarters` の issue #602。
このスキルの内容と #602 の表記がズレていたら、**#602 を正として直す**こと（ラベル名は
`Complexity` から `Difficulty` へ変更されたばかりなので、特に注意）。

## ラベルを付ける前に必ず覚えること（1行で全部言える基準）

**「このラベルが付いたら、誰の何の行動が変わるか」を言えないラベルは付けない。**

行動が変わらない飾りのラベルは、貼る時間の無駄になるので付けない。迷ったときは
「これを付けると何がどう変わる？」を自分に問い直す。

## Effort（作業量）はラベルにしない

`Effort: S/M/L` のようなラベルは**作らない**。その代わり「1issueは小さく分割する」を
原則として使う。issueが大きすぎるときは、ラベルではなく**分割の提案**をする
（→ ステップ1）。

---

## 判定の手順

### ステップ0: issue を全部読む

タイトル・本文・コメントを全部読む。親issue（parent）があれば親issueも読んで、
このissue単体で何を作れば終わりなのかを掴む。

### ステップ1（最優先・必ず先にやる）: 分割の合図（サイン）をチェックする

**「分割の合図」＝ issueが大きすぎるから割った方がいい、という警告のこと。**
以下の4つを**すべて**満たせるか確認する。1つでも満たせなければ、他のラベルを
判定する前に**分割を提案して、いったんここで止める**。

| 基準 | 満たしていると言えるか |
|---|---|
| ① 1つの成果物に対応している | 実装がPR1本で完結する（複数の独立した変更を1つのissueに詰め込んでいない） |
| ② 1人が中断なく終えられる | 他issueの完了待ち・仕様確認待ちで途中で手が止まらない |
| ③ 完了の定義が1文で言える | 「〜ができれば完了」と1文で言える（「〜と〜と〜ができれば」なら分割対象） |
| ④ 他issueの完了を待たずに着手できる | 依存先があるなら、それを別issueとして切り出せている |

**満たせないときにやること**: ラベルは付けずに、issueにコメントで分割案を書く
（子issueの案をいくつか提示する。実際に子issueを作る前に人間に確認を取ること。
理由は「新規作成の承認」参照）。分割してもなお大きいと感じる場合は、それ自体が
「方針決定が先に必要」というサインなので `要人間判断` を検討する。

**割り切れないときの倒し方**: 4つのうちどれか判断に迷う基準があるなら、
「満たせていない」側に倒す（＝分割を提案する）。分割しすぎて困ることはほぼ無いが、
大きすぎるissueをAIに丸投げする方が事故が大きい。

### ステップ2: Priority を決める（既存の4段階を使う。新しく作らない）

`Priority: Emerg / High / Middle / Low` は既に存在する。**このラベルが変えるのは
「複数issueの中で次にどれから着手するか」という順番だけ**。実装内容やレビュー方法は
変えない。

| ラベル | 目安 |
|---|---|
| `Priority: Emerg` | 今まさに困っている（本番が壊れている、顧客対応が止まっている） |
| `Priority: High` | 今週中に着手したい。締切や顧客都合がはっきりしている |
| `Priority: Middle` | 通常対応。特に急ぐ理由はない |
| `Priority: Low` | 後回しでよい。いつかやればいい |

**迷ったときの倒し方**: `Priority: Middle` にする。Priorityは順番しか変えない
（安全側のラベル）ので、根拠が薄いのに Emerg / High にして人を焦らせない。
逆に「本当に急がなくていい」と言い切れないなら Low にもしない。

### ステップ3: Difficulty を決める（どのAIモデルに任せるかが変わる）

| ラベル | 目安（こういうときに付ける） | 付いたら変わること |
|---|---|---|
| `Difficulty: Low` | 既存コードのパターン通りに直せる。参考になる似た実装がある | Haiku 4.5 に任せる。着手前レビュー無し |
| `Difficulty: Mid` | 複数のファイル・レイヤー（API・フロント・DBなど）にまたがる変更が必要 | Sonnet 5 に任せる。着手前レビュー無し |
| `Difficulty: High` | 既存の設計・データ構造に影響する、または新しい仕組みを設計する必要がある | Opus 5 に任せる。**着手前に人間が実装方針をレビューしてから着手** |

**迷ったときの倒し方**: 一段階上（難しい方）に倒す。`Low`か`Mid`か迷うなら`Mid`、
`Mid`か`High`か迷うなら`High`。理由は、難しい方に倒しても「レビューが1回増える」
だけで済むが、逆に簡単すぎるラベルを付けて弱いモデルに投げると手戻りが大きいため。

### ステップ4: 要人間判断 / AI完結可 を決める（マージ前に人が確認するかが変わる）

**このラベルが変えるのは「マージ前に人間の承認を必須にするか」の1点だけ。**
`要人間判断` は承認必須、`AI完結可` は承認を省略してよい、という意味。**必ずどちらか
一方だけを付ける**（両方は付けない）。

以下のどれかに1つでも当てはまれば `要人間判断`：

- 顧客（例: 高松市）との合意・確認が必要（仕様や見た目を変える等）
- 費用が発生する（新しいサービス契約、有償プランなど）
- 元に戻せない、または影響範囲が大きい（本番データの削除・移行、認証方式の変更など）
- 個人情報を扱う（氏名・所属課などの追加、閲覧権限の変更）
- 「何を作るか」自体の方針決定を含む（データモデルの命名規則、セキュリティ方針の決定など）

どれにも当てはまらなければ `AI完結可`。

**迷ったときの倒し方**: `要人間判断` にする。付け間違えたときの被害が非対称
（`AI完結可`にしてしまうと人の目を通さずマージされる）なので、確信が持てないなら
安全側＝人間の確認を必須にする方に倒す。

### ステップ5（当てはまる場合だけ）: 追加ラベル

必須ではないが、当てはまれば付ける。`要人間判断`とは別に付けてよい。

| ラベル | 付ける条件 | 変わること |
|---|---|---|
| `要顧客確認` | 顧客側の確認・合意が要る | 顧客への確認が取れるまで着手を保留する |
| `不可逆` | 本番データの削除・変更など元に戻せない操作を含む | マージ前の人間の最終承認を必須にし、自動マージを禁止する |
| `個人情報` | 氏名・所属など個人情報を扱う | マージ前にISMS担当のレビューを必須にする |
| `調査のみ（spike）` | 実装ではなく調査だけをするissue | 完了条件が「調査結果を報告コメントに書く」に変わる |

## 判定に迷う実例（3つ）

### 例1: 「ログイン画面が見づらいので直してほしい」
- ステップ1: 見た目調整のみ、成果物1つ、1文で完了条件が言える → 分割不要
- Priority: `Middle`（急ぎではないが放置もしたくない）
- Difficulty: `Low`（既存画面のCSS調整で完結。似た実装がある）
- ステップ4: 顧客の見た目には影響するが軽微な調整で、上の5条件に当てはまらない → `AI完結可`

### 例2: 「データモデルの名前を `Project` にするか `SaitaiProject` にするか決めて、移行する」
- ステップ1: 「名前を決める」と「移行作業をする」は別の成果物 → **分割の合図あり**。
  「① データモデルの命名を決める」「② 決めた命名へ移行する」の2issueに割ることを提案する
- （分割後、①の方は）Priority: `High`、Difficulty: `High`、`要人間判断`
  （命名・データ構造という方針決定を含むため）

### 例3: 「ユーザー情報に氏名・所属課を追加する」
- ステップ1: 成果物1つ、完了条件も1文で言える → 分割不要
- Priority: `Middle`
- Difficulty: `Mid`（DBスキーマ・API・フロントの複数レイヤーにまたがる）
- ステップ4: 個人情報を扱う → `要人間判断` ＋ 追加ラベル `個人情報`
  （Difficultyが低くても要人間判断になることがある。2つの軸は別物として判定する）

## 実行コマンド

### 初回だけ: ラベルの新規作成（★人間の承認が要る）

ラベルの新規作成は元に戻しにくい（後から消すと、既に付いたissueから消えてしまう）。
**作成する前に、作ろうとしているラベルの名前・色・説明の一覧を人間に見せて、
OKをもらってから実行する。** 一度作られたラベルは、以降のissueで使い回すだけなので
毎回の確認は不要。

```bash
REPO="geolonia/takamatsu-city-flood-prevention-headquarters"

# Difficulty（3色）
gh label create "Difficulty: Low"  --repo "$REPO" --color "0E8A16" \
  --description "既存パターン通りに直せる。Haiku 4.5 に任せる目安"
gh label create "Difficulty: Mid"  --repo "$REPO" --color "FBCA04" \
  --description "複数ファイル/レイヤーにまたがる。Sonnet 5 に任せる目安"
gh label create "Difficulty: High" --repo "$REPO" --color "B60205" \
  --description "設計に影響する変更。Opus 5 ＋着手前レビュー"

# 要人間判断 / AI完結可
gh label create "要人間判断" --repo "$REPO" --color "D93F0B" \
  --description "マージ前に人間の承認が必須"
gh label create "AI完結可"   --repo "$REPO" --color "0E8A16" \
  --description "マージ前の人間承認を省略してよい"

# 追加ラベル（当てはまるものだけ作ればよい）
gh label create "要顧客確認"        --repo "$REPO" --color "1D76DB" \
  --description "顧客側の確認・合意が取れるまで着手を保留"
gh label create "不可逆"            --repo "$REPO" --color "B60205" \
  --description "マージ前に人間の最終承認必須。自動マージ禁止"
gh label create "個人情報"          --repo "$REPO" --color "5319E7" \
  --description "マージ前にISMS担当のレビュー必須"
gh label create "調査のみ（spike）" --repo "$REPO" --color "C5DEF5" \
  --description "完了条件は実装ではなく調査結果の報告"
```

`Priority: Emerg / High / Middle / Low` は既に存在するので**作らない**。

### 通常運用: issueへの付与

```bash
gh issue edit <issue番号> --repo "$REPO" --add-label "Priority: Middle"
gh issue edit <issue番号> --repo "$REPO" --add-label "Difficulty: Mid"
gh issue edit <issue番号> --repo "$REPO" --add-label "要人間判断"
```

判定理由が際どかった場合（迷って安全側に倒したケースなど）は、付与コマンドを
実行するのと合わせて、issueに一言コメントで理由を残す
（例: `gh issue comment <issue番号> --repo "$REPO" --body "難易度は Mid/High で迷ったため、安全側で Difficulty: High にしました"`）。

### 既存ラベルと重複していたら

新しくラベルを作る前に、必ず一覧を確認する。

```bash
gh label list --repo "$REPO" --search "Difficulty"
```

- **同じ名前のラベルが既にある** → 作り直さず、そのまま使う
- **似ているが表記が違うラベルがある**（例: `Complexity: High` が残っている等）
  → 自分の判断で改名・削除は**しない**。人間に「表記ゆれがあります」と報告して指示を待つ

## やってはいけないこと

- 既存ラベルの**削除・改名**（`Priority: *` を含む、既にあるラベル全般）
- issue の**クローズ・タイトル変更・本文の書き換え**
- ラベルの**新規作成を人間の確認なしに実行**すること
- 1つのissueに同じ軸のラベルを**複数付ける**こと（例: `Difficulty: Low` と `Difficulty: High` を両方付ける、`要人間判断` と `AI完結可` を両方付ける）
- 分割が必要な（ステップ1で引っかかった）issueに、分割を提案せず**先にDifficultyだけ付けて終わる**こと
- 対象を決めずに**バックログ全件へ一括適用**すること（今どの範囲に適用してよいかは #602 の「既存issueへの付け方」を必ず確認し、不明なら人間に聞く）
- **実際にラベルを付ける作業そのものを人間の代わりに黙って進める**こと（このスキルは判定手順を提供するものであり、どの範囲のissueに適用するかは都度、人間の意図を確認する）
